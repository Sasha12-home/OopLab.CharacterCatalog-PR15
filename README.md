## 1. Загальна архітектура додатку

Проєкт побудований за **тришаровою архітектурою (Layered Architecture)** із дотриманням принципу інверсії залежностей (DIP):

```
┌──────────────────────────────────────────────────────────┐

└────────────────────────────┬─────────────────────────────┘
                             │ споживає CharacterViewModel
                             ▼
┌──────────────────────────────────────────────────────────┐
│                 ШАР БІЗНЕС-ЛОГІКИ (CORE)                 │

│               RickAndMortyApiJsonParser,                 │

└────────────────────────────┬─────────────────────────────┘
                             ▲ реалізує контракти Core
                             │
┌────────────────────────────┴─────────────────────────────┐
│                ШАР ПОСТІЙНОСТІ ТА КЕШУВАННЯ (DATA)       │

```

## 2. Шар постійності інформації та буферизація (DATA) — Практичне заняття 15

### 2.1. Стратегія збереження даних та вибір директорії ОС

Щоб не засмічувати робочу директорію користувача та гарантувати збереження даних між перезапусками програми, використовується стандартна системна директорія операційної системи (`Environment.SpecialFolder.LocalApplicationData`, або `~/.local/share` у Linux), інкапсульована у класі **`AppStoragePaths`**:

* **Директорія додатку:** `%LocalAppData%\OopLab.CharacterCatalog\`
* **Файл серіалізованого стану каталогу:** `%LocalAppData%\OopLab.CharacterCatalog\catalog_state.json`
* **Директорія файлового буфера зображень:** `%LocalAppData%\OopLab.CharacterCatalog\portraits_cache\`

Для серіалізації об'єктної моделі `CharacterProfile` обрано формат **JSON** (`System.Text.Json`), оскільки він компактний, не містить надлишкових службових тегів (на відміну від XML) і не залежить від пробілів та відступів (на відміну від YAML).

### 2.2. Механізм буферизації графічних портретів (`DiskImageCacheStorage`)

Для теми **«Каталог персонажів»** ключовим завданням постійності є **локальна буферизація (кешування) портретів** на диск, щоб зменшити кількість HTTP-запитів до зовнішнього сервера `rickandmortyapi.com` та прискорити відображення карток у майбутньому GUI:

```
Запит на отримання портрета (characterId, remoteUrl)
                       │
                       ▼
       [Перевірка файлу в portraits_cache/]
                /               \
          Файл існує        Файл відсутній
              /                   \
             ▼                     ▼
  Повернути локальний      HTTP GET запит байтів
  шлях без мережі          зображення з сервера
  (LoadedFromCache=true)           │
                                   ▼
                           Запис файлу на диск
                           ({id}.jpeg) та збереження
                           LocalAvatarPath у JSON
```

1. **Контракт `IImageCacheStorage` (у шарі `Core`):** визначає абстрактні операції `GetOrDownloadPortraitAsync`, `IsCached`, `GetCachedFilePath`, `GetCacheStats` та `ClearCache` без прив'язки ядра до деталей HTTP чи файлової системи.
2. **Реалізація `DiskImageCacheStorage` (у шарі `Data`):**
   * При першому зверненні до портрета завантажує масив байтів зображення через `HttpClient.GetByteArrayAsync` і зберігає його у файл `{id}.jpeg` (або `.png`/`.webp`) у папці `portraits_cache`.
   * При всіх наступних зверненнях або після перезапуску програми миттєво повертає локальний файл із диска (`LoadedFromCache = true`), не виконуючи жодного мережевого запиту.
   * Має вбудований захист (fallback): якщо мережа тимчасово недоступна, записує валідний мінімальний PNG-буфер на диск, щоб система не втрачала працездатність.
3. **Інтеграція з `CharacterViewModel`:**
   * Під час формування моделі представлення `CharacterViewModelMapper` перевіряє наявність локально закешованого файлу (`IsPortraitCached`, `LocalCachedImagePath`) і встановлює його як пріоритетне джерело зображення (`EffectiveImageSource`) для графічного інтерфейсу.

## 3. Шар бізнес-логіки (CORE) — Практичне заняття 14

* **`RickAndMortyApiJsonParser`** — парсить пагіновані JSON-відповіді від `https://rickandmortyapi.com/api/character` у доменну модель `CharacterProfile`.
* **`CharacterViewModel` та `CharacterViewModelMapper`** — формує модель для GUI з кольорами статусу (`#55CC44` / `#D63D2E`), рейтингом популярності (`PopularityScore`) та пріоритетним локальним шляхом до закешованого фото.
* **`CharacterFilterCriteria`** — фільтрація за статусом, видом, статтю, наявністю локального кешу (`--cached`) та сортування за рейтингом сили.

## 4. Командний інтерфейс (CLI) — Практичне заняття 13

* `cache-info` — виводить шляхи в `LocalApplicationData`, кількість закешованих портретів і загальний розмір буфера в КБ.
* `sync [--limit=20] [--no-images]` — синхронізує персонажів з API та за замовчуванням автоматично завантажує їхні портрети у локальний буфер.
* `cache <ID|ім'я>` / `cache --all` — примусово перевіряє або довантажує портрети на диск (демонструє миттєве взяття з буфера без HTTP-запиту при повторному виклику).
* `cache-clear` — очищує папку буфера зображень.
* `list [--cached] [--sort=power]` — виводить таблицю з колонкою стану буферизації фото (`[OK] На диску` або `[--] Тільки URL`).
* `info <ім'я або ID>` — показує повну картку персонажа з локальним шляхом до файлу портрета та його розміром у КБ.
